## 2. The stack, as given

- One Next.js 16 app (App Router, every page under `src/app/[locale]/`, API routes under `src/app/api/`), React 19, TypeScript 6 strict, Tailwind 4.
- SQLite through Prisma 7 with the better-sqlite3 driver adapter; the client is generated into `src/generated/prisma`; migrations are generated by `npm run db:migrate -- --name <what_changed>` and never hand-written; no enums and no CHECK constraints in SQLite, so allowed values are checked with Zod before a write.
- Zod 4 (`src/data/schemas.ts` holds a schema per data file; `src/data/load.ts` loads and validates them).
- Vitest 5 with a 60 % coverage gate on `src/domain`, `src/server`, `src/data` and `src/i18n`; each test file that needs a database copies a migrated template SQLite file (`tests/helpers/test-db.ts`).
- npm with `package-lock.json`; Husky hooks (pre-commit: secret scan, Prettier, ESLint on staged files; commit-msg: commitlint; pre-push: type check, tests, file size, no-AI); CI on every push and pull request runs the same plus formatting, coverage and the build, and lints every commit message in the pull request.
- Four languages, `en`, `fi`, `sv`, `et`, one JSON file each under `src/i18n/messages/`, a test holds the keys equal; `getT(locale)` with `{name}` placeholders; the locale is the first path segment.
- The API envelope: `ok()`, `fail()`, `ApiError`, `handleRoute()`, `readJsonBody()` in `src/server/api-response.ts`. The audit helper `withAudit()` in `src/server/audit.ts`: the write and its `AuditLog` row in one transaction. `todayIso()` in `src/server/today.ts` is the only clock.
- The domain folder `src/domain/` is pure by lint: no I/O imports, no `fetch`, no `process`, no `Date.now()`, no `new Date()`, no `Math.random()`. Dates come in as ISO strings, data as arguments, expected failures are values (`{ ok: false, reason }`).

**Our additions, and nothing else:** `fast-check` as a dev dependency for the property tests of smart problem 5, and the OpenAPI generator ported from the practice repo (Zod 4's `z.toJSONSchema`, no new package). Every other need is met by what is there.

**npm stays.** The practice repo moved to pnpm because four agents installed at once into fresh worktrees on a slow disk. Here the lockfile is small (about 620 packages), CI runs `npm ci` with the npm cache, the hooks call `npx --no`, and the README and the PR template say `npm ci`. Switching touches CI, the hooks and the docs for about half an hour and gains nothing once the slots exist. The trick that carries over is the **persistent slot**: each person's worktrees are created once at 16:30, `npm ci` runs once in each, and nobody installs again unless the lockfile changes (it changes once, for `fast-check`, in hour one). Fill every slot before the briefing ends.

**No third-party APIs to simulate.** The starter reaches no bank, register or broker: the outside world is the data pack and the calendar. The simulator's job in the practice repo is done here by three things, section 8: the clock with a demo override, data loaders that tests can substitute, and the scenario harness that encodes the judges' cards and the traps around them.

## 3. The rules

The organiser's rules (`RULES.md`), enforced by the hooks and CI, are the law: no AI in the product, conventional commits `type(scope): subject` (the scope names the slice), hooks never bypassed, pure tested domain, integer cents, one envelope, every change through `withAudit`, files under 600 lines, four languages, no secrets, CI green.

Our working rules on top, carried from the practice pilot:

1. **Test first.** The domain function's test file exists before the function; the test names the card or the trap it proves. A handler test mocks nothing it does not own.
2. **Contract first.** A slice's first commit is its Zod schemas (params, body, response) and its row in the route table; the others build against them before the handler exists.
3. **One owner per table and per shared shape.** The schema table in section 6 says who writes what. Another slice's rows are read through the owner's read function, never with a query on its table. A change two slices must make at one instant is an event inside the transaction (section 7), not a call.
4. **Dates are ISO day strings passed in.** `todayIso()` is called once per request in the page or the route and passed down; the demo override (section 8) lives there and nowhere else. No endpoint trusts a date from the browser except the demo override.
5. **Money is integer cents and the factor is integer millionths.** The coefficient has six decimals: multiply cents by the factor in millionths and divide once, rounding half up to the cent, in one function with the rule in its comment. Card 7's rent is exactly a half cent; floating point will land on the wrong side somewhere.
6. **Outcomes are codes with params, never sentences.** A decision reason, an end-of-term refusal, an early-exit line: the domain returns `{ code, params }`, the page writes it from the message files in the visitor's language.
7. **Nothing is hard-coded to a scenario card.** The three surprise scenarios take the same code paths with other ids. A test may pin a card's numbers; the code never knows the card exists.
8. **Write it down.** A decision goes into `docs/decisions.md` with its reason and what was chosen against; every agent task keeps a time log in `docs/log/<task>.md` (real clock: steps, commits, what blocked it, what it left undone); the README stays current in the same commit as the change.
9. **Waves.** Features are built in parallel waves, each agent in its own slot on its own slice, from a brief that names the base commit, the slot, the files it owns and does not own, the tests to write first, the time limit and the README sections to update. After every wave: one hardening agent (the tests that need the whole wave: the card runs, the property tests, the races) and one review-and-upkeep agent (the review written to `docs/reviews/`, every finding fixed, handed to an owner or accepted with a reason; the docs aligned) in parallel with the next wave.
10. **Done means** `npm run check:all` green, the tests of the change in the same commit, the route in the route table and the OpenAPI file regenerated, the message keys in all four files, the README section current, the time log closed.

## 4. The scope

**The spine (all seven, the entry ticket):** the catalogue with today's price (given), the sliders with the live monthly price, the application from `questions.json` with yes, no or manual review, the contract that locks the net rent, the monthly invoices from the contract, end of term (buy, return, pass on), the second life (a returned item re-priced and leased again).

**Smart problems, in the order we build them:**

1. **7 Circular impact**: the practice method (kg CO2e pro rata to the months of each later life) answers the brief's own question, "is the saving the same when the item was almost worn out". Swap in `co2-factors.json`; per item and for the fleet.
2. **1 Lock the price, not the tax**: the net rent is locked, VAT is the rate on the invoice date, the invoice says so in plain words.
3. **5 Money that adds up**: cents, the month-end rule, the first partial month, and the invariant "the invoices sum exactly to the contract total", proved by property tests over thousands of random contracts.
4. **6 Explain my price**: the breakdown (list price, down payment, financed amount, band and factor, net rent, VAT, buyout, total cost) and the side-by-side terms. It falls out of 1 and 5.
5. **2 Fair early exit** and **3 Second-life matchmaking** if the spine stands by Friday morning: both are pure functions one person builds alone (section 5 has the defaults).

**Wildcard:** the time-travel clock (the judges run ten dated cards) and the passport (every item's history across lives, the bonus of problem 3). The contract PDF only if there is time left on Friday.

**Not built, on purpose:** login (the starter has none: a "continue as" picker over `customers.json` sets the actor), the practice repo's hand-over model, bank reconciliation, reminders, strong identification, the simulator. If the briefing adds any of them, this list changes.

## 7. The events

The owner emits one event inside `withAudit`; the other slices register handlers; a handler that throws rolls the whole change back. No queue, no retries. ## 8. The clock, the data and the scenario harness

- **The clock.** `todayIso()` stays the only clock. A demo override (a cookie set from the demo page, or `?asOf=` on the demo routes only) lets the judges run a card dated in September 2026 or 2028. Pages and routes read it once and pass the day down; the domain never sees a clock.
- **Substitutable data.** The domain takes the price lists, the table, the rates and the curves as arguments, so tests feed variants: a price list v3, a VAT change on another date, a band that starts elsewhere. That is how the surprise scenarios pass: the code generalises because the tests already vary the data.
- **The scenario harness.** `src/domain/scenarios.test.ts` (or one file per card) encodes the ten cards with the pinned numbers below as table-driven tests against the real data pack, plus the traps the pack hides: the band boundary (`laptop-002` at 199 999, `laptop-003` at 200 000), the item below the lowest band (`ebike-010`), the item above the highest (`farm-006`), the reserved `ebike-009`, the broken business ID, both twin pairs of the waiting list, a VAT boundary invoice on 1 Jan 2027, a leap day, and every customer in `customers.json` applying for something. The demo page gets one button per card that seeds and runs it, so the pitch is a click and the judges' run is the same code path.
- **Property tests** (`fast-check`): for random contracts (any asset, any term, any down payment within the band, any start date in a range of years), the invoices sum exactly to the contract total, every due date is a real date, the February of a leap year is the 29th, and the balance at the end of the term equals the buyout within one cent per thousand euros.
